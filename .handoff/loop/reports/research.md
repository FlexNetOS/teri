## CRITICAL CONTEXT: What MiroFish Actually Is

MiroFish is NOT a self-contained simulation engine. It is a Python orchestration harness around the external OASIS library
(camel-ai/oasis), which implements the actual social-media agent simulation. MiroFish:

- Launches OASIS as a **Python subprocess** via `subprocess.Popen` (`simulation_runner.py:~line 180`)
- Monitors OASIS's JSONL output files for action events
- Wraps Zep Cloud (external SaaS knowledge graph) for graph/memory — `graph_builder.py:~line 45`, `from zep_cloud.client import Zep`
- Exposes a Flask REST API and Vue SPA as the UI layer
- Has NO tick-loop of its own; timing, agent logic, and action generation are all in OASIS

**Implication for the port:** Teri is a from-scratch Rust rewrite of the same *domain* (swarm prediction), not a translation of MiroFish's Python code. Teri implements its own tick loop, agent logic, and memory — these are already more complete than MiroFish's equivalent layer. The port work is primarily: HTTP API routes, the pipeline wiring (seed→graph→agents→sim→report), community platform adapters (Twitter/Reddit), and Zep→petgraph semantic equivalence.

**Missing behavior to add (small):** `<think>...</think>` stripping in `OpenAiAdapter::complete()`. Evidence: `llm_client.py:67` — `re.sub(r'<think>[\s\S]*?</think>', '', content).strip()`.

**Y-no-downgrade targets:** `src/llm.rs` test suite (20+ tests including `test_openai_complete`, `test_openai_stream`, `test_anthropic_complete`, `test_gemini_complete`). Any merge must not regress these.

### 2. Agent Structure / Persona / Memory

**MiroFish provides:**
Agent personas generated by OASIS (`oasis_profile_generator.py`, 48.5K). Agents are Twitter/Reddit-specific social media users with platform handles, follower counts, posting styles. Agent memory is managed by OASIS internally (not by MiroFish).

**Teri provides:**
`src/agent/mod.rs` (1524 lines):
- `Persona { name, background, traits, role }` with generic (non-platform-specific) fields
- `AgentState` enum: Idle/Thinking/Acting/Observing/Communicating
- `MemoryEntry { timestamp, content, importance }`, `AgentMemory { short_term: VecDeque<MemoryEntry> }`
- `Agent::step()` — full decision loop: memory retrieval (keyword overlap scoring), context construction, LLM call, action parsing, memory storage
- `Agent::prepare_action()` / `Agent::commit_action()` — read-write split for concurrent execution
- `AgentPool::spawn(n, graph, llm)` — generates N unique personas via `PersonaGenerator` with deduplication
- `PersonaGenerator` uses embedded minijinja template (`templates/persona_gen.jinja`)
- Full test suite: 20+ tests

**Classification:** `extend-Y`
Teri's agent framework is generic and complete for a domain-agnostic simulation. The port needs to extend it with:
1. **Social-media-specific persona fields:** platform handle, follower/following counts, platform (Twitter vs Reddit), posting style. These are in MiroFish's OASIS profile format (`oasis_profile_generator.py`).
2. **Social-media action types:** MiroFish/OASIS actions are `CREATE_POST`, `LIKE_POST`, `COMMENT`, `RETWEET`, `SEARCH_POSTS`, `DO_NOTHING` — teri's `Action` enum is `Speak/Move/Interact/Observe/Think` (generic, `sim/mod.rs:~line 30`).
3. **Platform-specific context construction:** agent context must include recent timeline posts, engagement metrics, not just a generic world state snapshot.

Teri's `Agent::step()` pattern and `AgentPool` machinery are fully reusable — extend persona fields and action enum, rewire the context builder.

**Y-no-downgrade targets:** `src/agent/mod.rs` test suite (`test_agent_step`, `test_agent_pool_spawn`, `test_persona_generator`, `test_action_parser_*`). Extending the Action enum may require updating match arms in these tests.

### 3. Simulation Tick Loop (SimEngine)

**MiroFish provides:**
No native tick loop. MiroFish launches OASIS as a subprocess (`simulation_runner.py:~line 180`, `subprocess.Popen([python_path, '-m', 'oasis.social_simulation', ...])`). OASIS owns the tick loop. MiroFish reads OASIS's JSONL output files to observe simulation progress.

**Teri provides:**
`src/sim/mod.rs` (780 lines):
- `SimEngine::run()` (lines 337-405) — fully implemented tick loop:
  - Phase 1: parallel `prepare_action` via `stream::iter + buffered(parallelism)` (tokio-native async)
  - Phase 2: sequential `commit_action`
  - God's-eye `inject_fn: Option<Arc<dyn Fn(u32, &mut WorldState)>>` called each tick
  - Broadcast send + snapshot hooks for SSE streaming
  - History push to `Arc<Mutex<Vec<WorldSnapshot>>>`
- `subscribe_with_history()` — broadcast receiver + catch-up replay buffer
- `register_snapshot_hook()` — hook for `StreamAdapter` integration
- Full test suite including end-to-end integration test with mock LLM

**Classification:** `reuse-Y`
Teri's SimEngine fully implements what MiroFish defers to OASIS. The core tick-loop contract (parallel prepare, sequential commit, world state, God's-eye injection) is present and tested. The port uses teri's SimEngine, not OASIS.

**Important open question (architectural):** MiroFish's OASIS integration provides dual-platform parallel simulation (Twitter + Reddit run as independent subprocesses, `simulation_runner.py` manages both). Teri's `SimConfig` has a single `parallelism` field for intra-tick agent concurrency. If the port needs inter-platform parallelism (two SimEngines running simultaneously, one per platform), the current SimEngine API is insufficient — this requires a top-level runner that owns multiple `SimEngine` instances. This is an **architectural decision for the owner/architect**, not a code gap that can be silently filled.

**Y-no-downgrade targets:** `src/sim/mod.rs` test suite (`test_sim_engine_run`, `test_subscribe_with_history`, `test_tick_buffer_*`).

### 4. Knowledge Graph

**MiroFish provides:**
External Zep Cloud SaaS (`graph_builder.py:~line 45`, `from zep_cloud.client import Zep`):
- `GraphBuilderService.build_graph()` — calls Zep API to create a graph, apply a dynamically-generated ontology (Pydantic models generated by LLM via `ontology_generator.py`), and add text as episodes (async processing on Zep's servers)
- `zep_graph_memory_updater.py` — writes simulation activity (agent posts, interactions) back into the Zep graph as new episodes, creating a live feedback loop during simulation
- `zep_tools.py` / `zep_entity_reader.py` — query the Zep graph for report generation (`insight_forge`, `panorama_search`, `quick_search` tools in `report_agent.py`)
- Zep's graph is episodic-memory aware: facts have validity windows (valid/expired), entities are auto-extracted by Zep's own LLM pipeline, and the graph updates asynchronously

**Teri provides:**
`src/graph/mod.rs` (1292 lines):
- `KnowledgeGraph` wraps `petgraph::Graph<Entity, Relation>` with dual indices
- Entity kinds: Person, Organization, Location, Concept, Event, Other
- Relation kinds: WorksFor, LocatedIn, RelatedTo, Causes, Affects, Other (with weight [0.0, 1.0])
- `entity_extraction_prompt()` / `relation_extraction_prompt()` / `parse_entities_json()` / `parse_relations_json()` — LLM-driven extraction helpers
- `get_subgraph(entity_id, depth)` — BFS subgraph extraction
- JSON and bincode serialization to disk
- **`KnowledgeGraph::build(doc)` IS A PLACEHOLDER** — only creates a single entity from document title (lines ~500-520). The full extraction pipeline (using the existing prompt helpers and parsers) is NOT wired into `build()`.

**Classification:** `extend-Y`
Teri has the petgraph infrastructure and LLM extraction helpers. What is missing vs Zep:

1. **`build()` pipeline is a stub** — must wire `entity_extraction_prompt()` + LLM call + `parse_entities_json()` + `relation_extraction_prompt()` + LLM call + `parse_relations_json()` into `build()`. The helpers exist; the orchestration does not.
2. **Episodic memory / fact validity** — Zep tracks whether facts are currently-valid vs historically-superseded. Teri's `Relation` struct has only a static `weight`. There is no temporal fact window. For the report agent's `panorama_search` semantics (current vs expired facts), teri needs a `valid_at: Option<(u64, Option<u64>)>` on `Relation` or a separate `Episode` wrapper.
3. **Live graph update from simulation** — `zep_graph_memory_updater.py` writes simulation events (agent posts) back into the graph during simulation. Teri has no equivalent `KnowledgeGraph::append_episode()`. For full MiroFish parity, simulation ticks need to write back to the graph.
4. **Semantic search** — Zep's `insight_forge` / `panorama_search` tools use vector search over the graph. Teri's `query_ltm()` is substring search (`memory/mod.rs:~line 300`); `query_vec_similarity()` returns `TeriError::Memory("vector similarity search not yet implemented")` (line ~320). Full semantic search parity requires embedding support.

The ontology generation (`ontology_generator.py`) is a MiroFish pre-simulation step to configure Zep's schema. In teri's petgraph model, entity kinds are a fixed enum — the ontology generation pipeline is not needed. This is a simplification, not a gap.

**Y-no-downgrade targets:** `src/graph/mod.rs` test suite (`test_knowledge_graph_build`, `test_entity_extraction`, `test_relation_extraction`, `test_get_subgraph`). Adding `valid_at` to `Relation` is a breaking schema change — must update all relation constructors and tests.

### 5. Persistent Memory Store

**Classification:** `reuse-Y`
For the port's core use case (agent long-term memory + world state persistence), teri's redb-backed `MemoryStore` is fully sufficient and more complete than MiroFish's file-based approach. The one stub (vector similarity) is not a port blocker unless the report agent requires semantic memory queries.

**Y-no-downgrade targets:** `src/memory/mod.rs` test suite (`test_memory_store_write_read`, `test_concurrent_writes`, `test_snapshot_roundtrip`).

### 7. Report Generation

**MiroFish provides:**
`backend/app/services/report_agent.py` (96.9K) — `ReportAgent` using ReACT (Reasoning + Acting) pattern:
- Phase 1: `plan_outline()` — LLM generates JSON outline (2-5 sections) from Zep graph context

- Tool dispatch: `_execute_tool()` routes to ZepToolsService methods

**Teri provides:**

- `PredictionReport { id, summary, timeline: Vec<TimelineEvent>, agent_highlights: Vec<AgentHighlight>, confidence, raw_query, created_at }`
- Does NOT query world state or graph memories — only uses `SimulationResult.history` snapshots

**Classification:** `extend-Y`
Teri's report generator produces a simple structured report from simulation history. MiroFish's `ReportAgent` is architecturally more sophisticated: multi-phase ReACT loop, Zep graph as the source of truth (not raw sim history), interactive chat, section-by-section streaming to files.

**Missing behaviors to add:**
1. **Graph-backed ReACT loop** — per-section tool calls against the knowledge graph (equivalent to MiroFish's `insight_forge`, `panorama_search`, `quick_search`). In teri's terms: section generation calls `KnowledgeGraph::search()` / `get_subgraph()` multiple times per section.
2. **Outline planning phase** — LLM generates section titles before generating content. Teri jumps directly to content generation.
3. **Interactive chat mode** — `chat_with_report()` with tool-augmented Q&A. Absent in teri.
4. **Progress file writes** — MiroFish writes section-by-section to disk for frontend polling. Teri's SSE stream is the only progress channel.

Teri's `generate_stream()` SSE mechanism is the right substrate for real-time section delivery; extend it with the ReACT loop and graph queries rather than replacing it.

**Y-no-downgrade targets:** `src/report/mod.rs` test suite. The streaming `generate_stream()` behavior (initial partial + buffer + early JSON parse) must not be regressed.

## Biggest Reuse Wins

1. **SimEngine (reuse-Y):** Teri's `SimEngine::run()` is a full tick-loop implementation with parallel agent execution, God's-eye injection, SSE hooks, and history tracking. MiroFish has NONE of this — it delegates everything to OASIS. This is the largest single reuse win. The port builds ON teri's sim engine, not alongside it.

2. **LLM adapter layer (reuse-Y):** Teri's three-adapter LlmClient trait with retry, streaming, and JSON mode is a strict superset of MiroFish's single-provider synchronous LLMClient. All MiroFish LLM calls map directly onto teri's `LlmClient::complete()` or `complete_json()`.

3. **Agent framework (extend-Y):** Teri's `Agent::step()`, `AgentPool::spawn()`, `PersonaGenerator`, and action parsing are complete and tested. The extension work (social-media fields + action enum variants) is additive, not a rewrite.

4. **Knowledge graph infrastructure (extend-Y):** Teri has entity/relation data structures, LLM extraction prompt helpers, parsers, serialization, and BFS subgraph. The `build()` placeholder is 20 lines of orchestration that needs writing, not a missing subsystem.
